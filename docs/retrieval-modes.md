# 四档检索与深度AI

## 模式行为

| 模式 | 实现 | 结果形式 |
| --- | --- | --- |
| 基础检索 `basic` | 扩大向量/关键词候选池、接口名和错误码精确匹配、过滤失效关键词索引、融合去重与来源多样性 | 原文片段，不调用对话模型 |
| 深度检索 `deep` | 基础检索加概念扩展、带标题/章节信息的重排、同文件同版本同章节上下文补全 | 原文片段，可展开较长内容，不调用对话模型 |
| AI 增强 `ai` | 保留原有检索、摘要注入、提示词及逐字输出路径 | 流式综合回答，仍是默认模式 |
| 深度AI `deep_ai` | 对话指代理解与问题拆解、多查询深度检索、覆盖度/冲突检查、按需补查一次、组织答案、证据与引用核验 | 阶段进度 + 核验后的最终答案 |

基础/深度检索仍使用 embedding；深度检索使用本地重排模型。这里“不调用对话模型”不代表不使用任何机器学习模型。新检索只在当前知识库取证，不混入缺少知识库归属的全局反馈库。

## 深度AI的边界

- 最近 6 条对话（每条最多 800 字符）用于解析“它”“上一种方式”等指代；旧回答不作为事实证据。
- 规划阶段的追问只是待验证建议，不会阻止检索。先查询当前知识库，再基于最终证据判断能否回答；补查为空时保留已有证据。
- “可能原因/常见问题/排查方向”先列出有依据的可能性和适用条件，缺少现场版本或日志不作为拒答条件。具体诊断先答可确认部分，再追问最少必要信息；不同产品、版本及安装/启动阶段分别说明。
- 仅检索后仍有关键歧义且没有可先回答的要点时才只追问。有命中时，该决定须由最终证据核验确认；无命中时说明证据不足，并可附上规划的澄清问题。生成和核验以用户实际问题为准，不把规划新增的要求当作必答项。
- 初始最多 3 条查询。规划改写不得丢失问题中的接口名、版本号、错误码。
- 候选去重兼顾来源和问题要点；同章节最多补前后各 2 段，每条证据最多约 6000 字符。邻段通过元数据查询，兼容原有索引的全局 chunk ID 与章节内索引差异。
- 召回与重排分别限量：默认最多精选 24 个候选做重排，每批 4 个，20 秒预算在批次边界检查；未完成重排的候选仍保留。去重使用预计算的连续字符片段特征，避免长 JSON/代码的逐字符比对耗时。
- 覆盖检查发现缺口或冲突后最多补查一次。补查保留原证据，并按完整问题重排，不进入无限搜索循环。
- 按操作、排障、对比、参数等问题类型组织回答；要求列出有依据的前提、限制、版本差异，明确未覆盖部分。
- 生成文本先缓冲，尝试完成一次模型证据复核和引用编号范围检查后展示。若仅自动核验超时，且草稿引用编号有效，则保留回答并在正文显著标记“自动核验未完成”（`unverified`）；明确不支持且无法修正、引用越界、生成失败或总超时，则回退到原文摘录。引用编号合法不等于语义正确；模型复核也不能保证零错误。
- 只有带有效文件快照且未过期的全局摘要可作为背景，摘要不能作为最终引用证据。
- 模型阶段有独立超时和总时限。用户取消会取消异步模型请求，检索线程在阶段边界停止；正在运行的本地模型运算不能被 Python 强制中断。
- 召回后立即保存证据，重排或生成超时仍可返回已找到的原文；超时明确标记为超时，不再误报“没有相关资料”。补查前为生成与核验预留时间。

## 配置

`config.yaml` 的 `qa.deep_ai` 默认值如下。旧用户配置缺少这些字段时，代码会使用同样的默认值，无需迁移数据库或重建索引。

```yaml
qa:
  retrieval:
    aliases: {}  # 可维护领域术语，例如 行情补发: [补包, replay]
    rerank_candidates: 24
    rerank_batch_size: 4
    rerank_seconds: 20
  deep_ai:
    top_k: 8
    context_chars: 20000
    max_tokens: 4096
    step_timeout_seconds: 20
    generation_timeout_seconds: 60
    verification_timeout_seconds: 45
    total_timeout_seconds: 180
```

界面发送的 top_k 优先于配置；默认最多保留 20 条证据。`context_chars` 限制证据正文总字符数，不是模型 token 上限；系统提示词、问题和少量元数据另占上下文。模型上下文较小时应降低此值。

通常需要 4 次逻辑对话调用（规划、覆盖检查、生成、核验），补查本身不增加对话调用。提供商失败重试、后备提供商和原有自动标题生成会增加实际请求数。深度AI的延迟与用量会高于原AI增强，应按真实业务问题比较收益。

## 接口与兼容性

- 同步 `/api/v1/qa/ask` 和 SSE `/api/v1/qa/ask_stream` 均接受四种 `mode`。优先级仍为请求参数、会话配置、默认 `ai`。
- 深度AI发送 `stage`、`sources`、`done`；最终答案位于 `done.answer`，不会提前发送未经复核的 `token`。`done.verification` 标记 checked/revised/unverified/extractive/insufficient/clarification/timeout。
- 新模式随会话和消息保存，导出/导入保留模式；更新消息时保留检索与深度AI的较长证据内容。
- 原AI增强的检索策略保留。共用客户端修正了提供商异常类不一致的问题：首个 token 前失败可切后备提供商；已输出内容后失败中止，避免拼接两个模型的半份答案。

## 验证与后续评估

自动测试覆盖关键词零/负分、精确标识符、知识库隔离、失效索引过滤、真实 Chroma 章节查询、证据去重、规划失败、补查上限、引用越界、核验失败、超时/取消、同步与 SSE、会话导入导出及提供商失败处理。

这些测试验证流程与约束，不代表已实测真实问答准确率。正式评估建议选取 20–30 个代表问题，为每题记录必须覆盖的要点、正确原文位置和不可编造的条件；对比原AI增强和深度AI的要点覆盖、无依据结论、引用正确率、响应耗时与模型用量。
