# MCP 对比报告后的修复与独立验证

## 问题与修复

下游报告的约 50 秒慢查询，服务日志显示主要耗时为 embedding 模型加载时 Hugging Face SSL 重试，随后降级关键词查询。现有知识库登记 bge-large / 1024 维。本轮最初按文件扫描误判 large 缺失；其 snapshot 文件实际是符号链接，普通 rg --files 扫描未列出。随后使用 Hugging Face 缓存解析器确认 large 完整缓存已存在，授权重启后约 2.9 秒成功加载 1024 维模型。实际原因是按远程模型名加载时仍探测可选文件，并非已确认缺少权重。

本轮修复：

- 完整模型缓存以本地 snapshot 路径、local_files_only 加载，避免探测远程可选文件。
- 普通查询和启动预热不自动下载缺失模型；快速返回可恢复错误。管理员通过现有模型加载/切换入口明确操作，仍可下载缺失文件，不绕过现有权限与预检。
- 加载失败按模型冷却 60 秒，避免重复加载；管理员显式加载可绕过冷却。成功后清除失败状态。
- embedder 构造和实际预热分离，只有成功加载才记录预热完成；失败不再被吞掉后误报成功。
- MCP 返回当前调用关键阶段计时，标注阶段可能包含/重叠、计时截至输出分页前，不冒充端到端耗时。request_log_key 对应 request_id。
- 返回 requested match_mode、实际 executed_paths、degraded、失败阶段、恢复建议和冷却提示。结果相关性不足时也提示 Agent 使用原文语言 query_variants、目录和原文。
- 并发仍按独立配置执行，没有扩大默认并发或引入排队。cursor 与 scan_cursor 的区别沿用已实现契约。

真实模型合成数据测试：3 份英文短文，内容为固件操作、债券、午餐；真实 Chroma + 关键词索引 + MCP execute。bge-base 首次加载约 2,404ms，输出 768 维。

语义候选仍包含另一份非目标文档，本实验只证明真实模型加载、召回和降级链路，不证明排序最优、答案质量提升或原千万字符库能达到相同耗时。完整扫描链无损性由现有有界扫描续接测试覆盖；未冒称已在真实原库完成全量枚举。

## 复现

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest tests/test_mcp_access.py -q
.venv-mcp/bin/python -m tests.mcp_gateway_check
.venv/bin/python -m tests.mcp_real_embedding_check --model-dir /absolute/path/to/deployed/model/snapshot
```

最后一项必须使用已部署、只读的完整 snapshot。它自动创建并清理临时配置/数据库/索引；不会下载模型，不改变现有模型选择。

## 兼容、回退与剩余工作

共享 embedding 加载器的行为有一项明确变化：普通查询不再隐式下载模型。首次部署需提前准备模型，或通过管理员模型加载入口下载。完整缓存的模型标识、权重、归一化和维度不变；API embedding 模式不变。无数据库迁移、无模型替换、无索引重建。回退代码即可恢复旧加载行为；旧行为也会恢复查询期间联网重试的风险。

用户确认后已重启本地 8000/8001，沿用原数据与原模型配置；bge-large 的 1024 维模型成功预热。没有切换模型、下载权重或重建索引。缺失模型降级属于隔离故障场景，不代表当前原库仍缺模型。原千万字符库的下游回答效果仍需 Claude Code + GLM 独立复测。未提交、未推送、未操作生产。

## 重启后 bge-large 独立补验

使用与原库同型号的 bge-large snapshot、独立临时索引和合成短文，再次禁止 HTTP 网络请求。加载 2594.07ms，维度 1024；9 次成功查询均包含 vector 路径且无降级警告。

| 场景 | 三次耗时 ms |
| --- | --- |
| semantic，无变体 | 164.96 / 150.84 / 159.82 |
| semantic，带英文变体 | 153.26 / 143.45 / 139.94 |
| hybrid，带英文变体 | 152.41 / 147.34 / 150.32 |

同样的缺失模型故障样本快速降级：49.49 / 49.95 / 57.54ms。仍为 3 份合成文档，不能据此推断原知识库性能或最终回答质量。
