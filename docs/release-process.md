## 发布身份与平台选择

- 提交、发布、部署是三个独立动作，不互相隐含完成。
- 每次构建可以独立选择 Windows、macOS、Linux 的任意组合。
- 同一版本的所有平台产物必须来自同一个固定提交。
- 未选择或未通过验证的平台标记为未发布，不使用旧安装包冒充新版本。
- 后续补构建某个平台必须检出原版本提交，不能使用届时最新 main；构建依赖和工具链也应记录并复用。
- 每次产物记录版本、完整 commit SHA、平台/架构、构建工具与依赖、SHA256；镜像同时记录镜像身份。
- 已发布标签和产物不得静默覆盖。修复代码或构建内容变化需要明确的新候选版/版本及验证。
- 版本号采用单一权威来源，前端、后端和打包元数据从它派生并校验。
- 历史本地标签已有 v0.1.1、v0.1.2，当前程序版本仍为 0.1.1；不得覆盖旧标签。当前版本继续保持 0.1.1；后续版本（例如 0.1.2）须用户单独确认，且先检查同名历史标签，不能覆盖。

## 开发至部署

1. 明确范围，从 main 创建功能或修复分支；不直接修改生产代码。
2. 完成相关测试、前端构建及必要页面检查，提交并审查差异。
3. 合并后固定发布提交，从干净源码构建候选产物，禁止夹带未提交文件或本地密钥。
4. 使用独立数据和配置验收。Linux 验证整个应用与代理组合；桌面版验证安装、启动、退出及升级。
5. 验证登录权限、文档导入、索引、检索、流式响应等关键流程。涉及 AI 效果时使用少量固定问题并记录模型和配置，不要求文本逐字一致。
6. 正式发布经过验收的同一份产物；生产服务器不重新构建。若源码或产物改变，重新生成候选并验证。
7. 部署前检查环境、备份数据、确定迁移兼容性和回退步骤；部署后检查页面、接口、日志及资源。
8. 记录每台服务器实际版本、提交、镜像、配置差异与验收结果。保留上一版产物和必要备份。

候选版与正式版的命名、标签机制必须保证“同一产物晋级”，不能在验收后仅为改版本号而重新打包未经验证的产物。

## Linux 交付

- Docker 镜像包含应用及运行依赖；容器是运行实例；离线部署包是镜像、模型、配置模板、脚本和必要运行时安装材料的集合。
- 提供完整离线安装包与应用升级包。模型单独管理并记录版本和校验值，未改变时不重复传输。
- 数据、原文、数据库、向量库、账号、API 密钥等独立持久化，不打进通用镜像。
- 计划将 Nginx 与 Insight 分为两个容器，由 Compose 统一管理；当前旧部署尚未迁移到此结构。
- 前端入口、应用都需有明确的启动、退出、重启恢复和日志管理，避免应用已启动但代理未启动。
- 部署前检查宿主机路由和公司内网网段，避免容器网络地址段冲突。后端默认不直接对外暴露。
- 内外网环境共用产物，但各自维护配置与数据；不得硬编码某环境的 API、DNS 映射或账号。
- 不在 4GB 公网生产机额外常驻完整测试环境；主要 Linux 验证在本地完成，生产做小规模验收。
- 数据结构变化必须评估回退兼容性；换回旧镜像不一定能恢复旧数据格式。
- 生产部署保留明确确认步骤，不设置提交代码即自动上线。

## 换行符与构建校验

- 用 .gitattributes 固定规则，不能依赖开发者机器的 Git 默认配置。
- Python、前端源码、JSON、YAML、Dockerfile 默认 LF；Linux .sh 必须 LF，并检查所需执行权限。
- Windows .bat、.cmd 使用 CRLF；模型、图片、压缩包等二进制文件禁止文本转换。
- 换行符规范化单独提交，不混入功能修改；先审查差异，再执行批量规范化。
- 源码分析可区分 CRLF/LF 差异；产物 SHA256 校验必须按原始字节，不得忽略换行符差异。
