# 模型能力与问答预算统一方案

日期：2026-11-12。状态：核心预算约束、前台设置与空间分配已在本地实现，尚未部署、提交。

## 本轮实现与边界

- 新增统一预算模块；复用已有模型容量和最大输出，冻结问答预算，权限仍动态校验。
- 工具调用按最终协议 payload 估算；账号普通聊天/流式调用按 messages 估算并约束输出。普通路径的协议附加字段未全部纳入估算，保留 3000 tokens 边距；UTF-8 字节估算不是供应商精确 tokenizer。
- 增强/深度问答分离作答预留与输出封顶；深度问答在空间不足时提前使用现有证据压缩机制。
- 系统设置新增上下文与会话记忆表单（含作答预留），显式保存、新请求生效、覆盖来源提示。旧配置按字段兼容，正确路径优先。
- 预算原因写入系统日志、ToolChat 调用诊断与会话上下文信息。**独立 AI 日志详情页的完整预算展示尚未实现**。
- 普通 Responses 和工具 Responses 均区分输出耗尽与其他 incomplete 原因。
- 文档摘要保留现有 summary_policy；非账号旧 LLMClient 路径未统一接入新末端保护。当前优化覆盖账号模型与 ToolChat。
- 不新增数据库表；不改动 176/224。尚未进行真实供应商最大窗口压测，模型容量未填写时仍可能被供应商拒绝。
- 回退使用原版本代码即可；保留 YAML 与已有模型能力数据。旧版本不遵守新增问答模型上限，回退时仍须确保全局 max_tokens 不超过实际供应商限制。

以下为原始设计与验收范围，未列入上面已实现项目的内容作为后续增强。

## 结论

复用 API 模型编辑中的 `context_tokens`、`output_tokens`，将其从文档摘要扩展到问答和其他模型调用。增加统一的预算解析与请求前检查；分别管理模型能力、任务输出封顶和作答预留。先补齐能力约束和配置可见性，再调整资料装配策略。

不根据 GLM、DeepSeek、GPT 名称硬编码额度；同一模型在不同 API、中转和账号套餐下可能不同。能力按现有 API + model_id 维度保存。

## 已核实的现状

| 调用路径 | 当前行为 | 缺口 |
| --- | --- | --- |
| 模型选择与权限 | `accounts.resolve_provider()` 已带出两项能力，`provider_snapshot` 保存当前模型信息 | 数据已具备，无需新建一份能力配置 |
| 模型编辑 | 页面明确标注“模型能力（可选，摘要预算使用）”；数据库 `api_model_limits` 保存能力 | 需要扩展用途和说明，不是仅修改文案 |
| 文档摘要 | `summary_policy.effective_policy()` 已按模型输出和上下文约束任务参数 | 保留已有分段、补偿输出、检查点策略，复用统一能力来源 |
| 增强 AI | `chat_options()` 取系统输出上限与全局窗口一半的较小值 | 没读取模型能力；窗口的一半是隐藏限制 |
| 深度 AI | 查阅轮次与最终作答都动态扣除输入估算及边距 | 未限制模型最大输出，完整查阅记录可能挤占最终作答空间 |
| 会话记忆摘要 | 输出使用 `qa.conversation_context.summary_tokens`，总超时固定 90 秒 | 也需遵守模型能力；不能套用文档摘要的任务参数 |
| 工具/联网测试、标题等辅助调用 | 各场景传入较小的固定或专用输出额度 | 统一末端能力检查，保留场景自身预算，不改成问答大额度 |
| 参数发送 | ToolChat 直接使用调用方额度；Responses 映射为 `max_output_tokens`，其他现行路径使用 `max_tokens` | 需要请求前统一约束；参数映射保持协议适配器负责 |
| 预算估算 | 当前按 UTF-8 字节数 / 3 估算，部分位置分别序列化，口径不完全一致 | 不能当作供应商实际用量；最终请求含额外系统/工具字段，需要统一估算口径 |
| 流式终止 | 一些路径把所有 Responses `incomplete` 都当作输出耗尽 | 应检查具体原因；未知原因不能宣称耗尽 tokens |

176 的两个问题属于不同层次：6996 是剩余窗口限额；161920 被拒绝是超过该接口允许的最大输出 131072。扩大窗口不能修复最大输出约束，降低输出也不能解决输入占满窗口。

## 配置的职责与优先级

### 模型能力

- 上下文容量 `context_tokens`：该 API 下所选模型的容量约束。
- 最大输出 `output_tokens`：该模型单次生成的输出限制。
- 留空继续表示未知；不自动填写推测值，不以一次连接成功认定容量正确。
- 当前数据库已有字段，第一阶段不新增数据库结构。

### 系统与场景策略

- `qa.ai_generation.max_tokens` 继续作为问答单次输出封顶，兼容旧配置。
- `qa.conversation_context.context_window_tokens` 在页面明确标为“模型容量未知时的默认窗口”；已填模型容量时优先使用模型值。
- 第一版保留应用现有 262144 窗口支持上限，作为明确的实现边界；模型填写更大容量时显示实际使用上限，不能静默截断。以后扩大须单独验证。
- 近期历史、会话记忆摘要、增强 AI 原文等预算继续分工，不混用 tokens 与字符。
- 本轮开始时冻结模型能力和预算策略；保存只影响新请求。账号、API、知识库权限撤销仍即时检查，不能因快照而延后撤权。

### 每次请求的计算

```text
有效窗口 = min(模型已填容量，否则系统默认窗口, 应用支持上限)
输出封顶 = min(当前场景配置额度, 模型最大输出〔已填时〕)
剩余空间 = 有效窗口 - 完整请求输入估算 - 安全边距
实际输出额度 = min(输出封顶, 剩余空间)
```

模型最大输出未知时，只能使用场景上限与剩余空间，不能承诺不会被服务商拒绝。第一版保持旧配置可继续运行并显示“能力未配置”，不统一偷偷降到 8192，也不强制禁用旧模型。

若剩余空间非正或不足以完成所需任务，先回到上层压缩/选择资料；不再用 `max(1024, remaining)` 强行制造一个可能超窗的请求。

## 作答预留与资料装配

输出封顶并不等于每次要占满该额度，也不应按 131072 全额预留，导致没有空间查阅资料。

建议第二阶段引入“作答预留预算”高级设置：初始建议 16384 tokens，最终默认值经隔离回放确认；始终不超过模型/场景输出封顶。它表示查阅规划时尽量保留的空间，不保证模型一定生成这些 tokens，也不是额外增加在输出上限之外的额度。

深度 AI：

1. 每轮工具调用前，用本轮预算快照检查容量，并预留最终回答空间。
2. 工具结果到达后再检查；一轮可能返回多个结果，不能只在调用前估算。
3. 若完整上下文满足作答预留，继续保留原生工具记录；若不满足，则停止补查并使用现有 `evidence_state.answer_payload()` 构建压缩作答资料。
4. 压缩保留整条证据、稳定引用编号和省略清单；不得剪断工具调用/结果配对，或删改协议要求回传的推理及签名字段。必要时建立合法的独立作答输入。
5. 如果系统提示、问题和必要证据本身过大，明确报告预算不足；不静默删掉核心问题继续回答。

增强 AI：统一按模型容量规划历史、资料和输出，逐步替换固定“窗口对半分”。第一阶段先保留原装配策略，仅加入模型硬上限，降低一次修改的回归范围。

推理块、加密推理与网关附加字段的计数不能简单等同自然语言正文。第一版保留保守估算，记录估算版本与实际 usage（服务商提供时），不新增在线 token 计数依赖，不为估算删除协议必需数据。

## 前台布局

| 位置 | 内容 |
| --- | --- |
| 个人/团队 API → 编辑模型 → 模型能力 | 复用上下文容量、最大输出；说明适用于问答、摘要及辅助调用；展示未知或已配置，不新增第二套字段 |
| 系统设置 → AI 运行配置 → 问答生成 | 输出封顶、时长等现有字段；解释实际额度还受模型能力和剩余窗口限制 |
| 系统设置 → AI 运行配置 → 上下文与会话记忆 | 未知模型默认窗口；高级折叠项放近期历史、会话摘要输入和输出预算；第二阶段增加作答预留 |
| 对话详情 → 上下文使用情况 | 实际窗口、输入估算、实际输出额度、限制来源；只显示当前账号本轮请求信息 |
| AI 调用日志详情 | 配置输出、模型输出限制、有效窗口、实际发送额度、是否压缩、终止原因；支持排查，不展示额外推理正文或密钥 |

系统页没有唯一“当前模型”，不把某个管理员选中的模型误当全局模型。预算示例应明确选择模型或注明是示意，真实生效值以本轮调用详情为准。

设置保存使用明确保存按钮、成功反馈和“新请求生效”提示；上下文接口保存后同步内存，重启保留。沿用 `system.view/system.edit`；模型编辑沿用个人/团队 API 的现有权限。覆盖文件存在时展示来源和冲突，避免保存成功但被覆盖。

## 错误与可观察性

- 上下文不足：“本轮资料占用较多，输出额度由 X 缩减至 Y”；已经压缩时注明处理结果。
- 已知模型输出封顶：“已达到该模型配置的输出上限 X”，不一律建议增大系统上限。
- 服务商参数拒绝：记录脱敏错误和调用编号，提示核对该 API 模型能力；不解析任意报错文本后自动改配置。
- 无正文且截断：只有服务商用量明确支持时才描述推理消耗；否则使用“输出达到限制但未产生可见正文”。
- 连接中断、超时、服务商拒绝和真正输出截断使用不同原因；Responses 的非 token 原因 incomplete 不归类为额度耗尽。
- 第一版不自动重复执行问答、不自动续写，避免重复工具动作或正文。保留用户主动重试。

## 实现边界与兼容

建议新增纯预算模块（例如 `src/core/model_budget.py`），输入能力快照、场景策略及输入估算，返回决策和原因；不读取数据库、不选择模型、不处理业务权限。

上层负责提前组织输入；原生工具调用和普通聊天发送前都使用同一模块作最后校验。末端不得随意裁剪业务消息。文档摘要保持现有任务策略，通过公共能力解析获得约束；检查点签名继续反映实际影响摘要内容的预算。

兼容规则：

- 无模型能力的旧配置保留可用；已填写能力后问答开始遵守，最大输出变小属于预期行为，页面说明清楚。
- 正确的 `qa.conversation_context` 优先；只有缺少对应字段时才考虑旧 `feature_flags.conversation_context` 中的四个已知预算字段。其他混入开关不搬迁、不删除。
- 写入统一到正确路径；现有 config.local 覆盖规则不变，冲突显式处理。
- 不自动把 176 的 262144/131072 写成所有安装或所有模型的默认值。
- 第一阶段无需数据库迁移；回退代码时，新写的正确 YAML 字段和原模型能力字段仍可保留，旧版本会继续忽略问答模型能力限制，回退时必须保留合适的全局输出封顶。

## 实施顺序

1. **统一能力约束**：接通模型能力快照、公共预算计算、工具与普通请求前校验；覆盖增强/深度问答及辅助调用，保持现有摘要任务策略。补充限制来源与错误分类。
2. **补齐前台**：上下文配置接口与表单、模型字段说明、配置来源/生效提示、调用详情。与第一步作为同一候选版本验收，避免界面先宣称支持。
3. **改善空间分配**：作答预留、深度 AI 压缩触发点、增强 AI 装配策略，独立回归及真实模型验证。
4. **后续高级设置**：术语、重排、分块等按 `configuration-ui-backlog.md` 单独安排，不合并成此次预算修复。

## 验证与验收

- 精确复现 176 两种情形：系统输出 161920、模型输出 131072 时，实际 payload 不得超过 131072；小窗口被资料占满时，触发压缩或清晰报错，不直接用仅剩额度冒充足够作答。
- 能力为空、仅填一项、模型容量小于默认值、模型容量大于默认值、超过应用支持上限、零/负剩余空间。
- OpenAI 兼容、Responses、Anthropic/Arch 各现有协议；验证发送字段、工具定义与工具结果配对保留，原生搜索附加字段计入预算估算范围。
- 增强/深度 AI、会话记忆摘要、文档摘要、标题和能力测试均遵守模型上限；辅助调用不会被意外扩大为问答额度。
- 保存后新请求使用新预算，运行中请求使用原快照；并行用户/模型不串配置，撤权仍及时生效。
- 所有模型测试使用隔离数据及模拟服务；候选完成后对实际接入的 GLM、DeepSeek、GPT 各做小规模授权验证。小请求通过不能宣称真实最大窗口已验证，不主动填满 262144 做容量压力测试。
- 通过针对性和现有回归测试、前端类型/构建检查及变更 lint 后，再决定部署；本方案本身不部署。
